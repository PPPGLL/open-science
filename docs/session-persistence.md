# Session persistence: ownership and lifecycle

This guide describes the implemented contract for contributors adding Session fields or changing a
save path. It does not grant new write authority or propose a common merge/state-machine framework.
The public entry points and their behavior tests remain the executable contract.

## Where each fact belongs

| Surface                                     | Responsibility                                                                                                                                                        | Important boundary                                                                                                                                                                                                                                |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sessions/<projectId>/<sessionId>.json`     | Durable conversation graph, Session preferences, runtime recovery snapshots and artifact references. The directory supplies the owning `projectId` on load.           | `conversationGraph` is canonical in v2 writes. Flat `messages`, `activities` and `activityGroups` are synchronized active-Branch compatibility views, not independent histories. File references do not own native Artifact/Upload version bytes. |
| SQLite `Session` and related projections    | Summary/list/search/usage reads, assigned Session number, revision and archive projections, and deletion tombstones.                                                  | Metadata copied from JSON can be reconciled, but the database also owns number allocation and deletion evidence. Do not discard the database as a cache.                                                                                          |
| SQLite write/recovery and independent facts | `SessionNumberSequence`, `PendingSessionReconciliation`, projection completion state, and `SessionAuxiliaryTurnUsage`.                                                | Pending intents survive a missing Session row. Auxiliary usage is an independent fact; deleting an unpublished allocation requires proving it has no such evidence.                                                                               |
| Session manifest                            | Last-open Project/Session selection.                                                                                                                                  | Navigation restoration is separate from Session content and from whether every recovery subsystem is healthy.                                                                                                                                     |
| Main owners and Renderer store              | Main serializes mutations and owns runtime/delegation protocols. Renderer holds hydrated projections, local edits, streaming buffers and selected conversation state. | An in-memory snapshot or notification is not a durable save receipt. Not every Renderer field is serialized.                                                                                                                                      |

## Save paths are deliberately different

1. **Create or ordinary whole-Session save.** The application save boundary authorizes message
   attribution, and `SessionPersistenceCoordinator` verifies identity and serializes the operation.
   `SessionPersistenceStateOwner.saveSessionWithAuthority` loads durable authority, checks/rebases
   the Session revision, protects Main-owned fields, materializes the graph, upgrades legacy uploads
   when needed and validates finalized Artifact bindings before calling the repository.
2. **Dedicated mutation.** Runtime-context patches, Session details, Specialist binding, Compute
   settings, delegated work, side chats, Task completion and archive commands load/update their
   own authority. They do not inherit permission to replace unrelated Session fields. For example,
   `updateSessionConfiguration` requires no `activeRun` and an `idle` or `error` Session, whereas
   ordinary saves also serve ongoing transcript persistence.
3. **Repository publication.** With SQLite projection enabled, `prepareSave` reserves a number and
   records pending reconciliation; durable JSON publication precedes `commitSave`. The repository
   returns the saved Session, including its actual revision and assigned number, or rejects.
   `saveSessionWithRevision` forwards that result; it cannot synthesize a receipt from `void`.
4. **Post-publication consumers.** The state owner records the returned Session, captures provenance
   and updates the file index. A later index/provenance failure can reject the application operation
   after JSON was saved. Failure is therefore not proof that the old JSON is still on disk. Refresh
   authority before deciding what to retry. Notification delivery is a separate derived effect.

### Whole-Session field handling

means a durable Session was found; creation has no older value to preserve. Ordinary fields still
pass revision, graph, attribution, imported-history and finalized-binding validation.

| `id`, `projectId`, `number`, `revision`                                                                                                                                                                                                                                                                                                    | Identity checks reject cross-Project reuse; incomplete ownership scans fail closed. SQLite preserves its assigned number. The repository compares an expected whole-Session revision when supplied and stamps the next revision.                                     | A new identity must be available. SQLite allocates the number; the submitted revision is not a confirmed save result.                                                                                                                       |
| `packageOrigin`, `branchSource`                                                                                                                                                                                                                                                                                                            | Imported history is constrained by `preserveImportedSession`; an ordinary save cannot invent an import marker. Existing `branchSource` is retained, including its absence.                                                                                           | Branch creation records the source snapshot. Historical Sessions are not retroactively given branch provenance. Package import has its own authority path.                                                                                  |
| `title`, `description`, `sessionDetailsSource`, `sessionDetailsGeneration`                                                                                                                                                                                                                                                                 | Once durable details source or generation metadata exists, all four come from Main despite a Renderer snapshot. Otherwise the ordinary path can establish fallback copy.                                                                                             | [Session details owner](../src/main/session-details/owner.ts) owns later details transactions. `sessionDetailsGenerationEligible` is a one-shot marker for new root Sessions; legacy/branched Sessions do not gain eligibility by default.  |
| `runtimeContext`, `planHistoryProjections`                                                                                                                                                                                                                                                                                                 | Submitted runtime context is removed even on creation. | `status`                                                                                                                                                                                                                                                                                                                                   | Normally follows the submitted runtime projection, with Main-owned waits overriding it. ### Stale saves and Renderer updates

For a stale ordinary save, `resolveRevisionedSessionSave` accepts an explicit preference rebase only
when the submitted and durable **materialized conversation graphs are equal**. Otherwise it throws
a revision conflict. The Renderer allowlist is exactly `title`, `permissionProfile`,
`autoReviewEnabled`, `memoryEnabled`, `agentConfiguration` and `pinned`. Main has an additional paired
Specialist-binding path. A preference rebase preserves a requested `branchContextResetRequired`
barrier rather than acknowledging provider reset. A finalized-binding conflict has a separate
safe-field rebase and revalidation path; it does not authorize replacing bound history.

See [revision conflict handling](../src/main/session-persistence/revision-conflict.ts) and
[Renderer option sanitization](../src/main/session-persistence/renderer-save-options.ts).

The return trip is also an ownership merge. The Renderer keeps unsaved local titles and streaming
state, orders archive/Compute projections by durable revision, and handles runtime/files authority
and graph identities separately. An update with an older activity timestamp can still contain
useful durable authority; dropping every older snapshot is not the contract. When incoming runtime
authority owns frame conflicts, the identity merge retains the current root frame's `activeBranchId`.
Other branch/event paths have their own selection rules; resolve messages from their owning
frame/branch.
The [persistence owner](../src/renderer/src/stores/session-store-persistence-owner.ts) and
[identity merge helpers](../src/renderer/src/stores/session-store-persistence-merge.ts) implement
these rules. Their behavior is distinct from Main's authorization of a save.

## Archive and deletion operation matrix

Archive is reversible visibility plus work admission. Deletion has separate durable intent,
tombstone and cleanup protocols. Neither replaces the other with a universal Session status enum.
The [archive coordinator](../src/main/archive/coordinator.ts) serializes admission and archive
transitions per Project; it does not hold its queue for an entire prompt execution.

| Operation                                     | Existing admission/transition rule                                                                                                                                                                                   | Result and retry boundary                                                                                                                                                                                                    |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Start/admit work through Session availability | Resolve the Session's Project owner; reject owner mismatch, an unavailable/deleting/archived Project, exported Session, imported read-only history or archived Session.                                              | Fresh runtime identity can help resolve a Session owner; an unresolved owner fails closed. Execution owners retain their own additional checks.                                                                              |
| Archive a Session                             | Owning Project must be active. Reject `running`, `waiting-for-user`, `waiting-permission`, `waiting-plan-approval`, current running delegated attempts, answerable delegated questions or busy runtime/Compute work. | Compare expected Session revision before changing visibility. Activity checks include async Compute queries and rechecks; background work is cancelled after the durable transition.                                         |
| Archive a Project                             | Reject deletion/import/export conflicts and busy Project runtime. Its Session catalog must be complete and all children pass archive eligibility.                                                                    | Set Project archive state; do not rewrite every child's `archivedAt`. Background work is drained; read-badge failure does not undo archive.                                                                                  |
| Restore a Session                             | Its Project must already be active, and the expected Session revision must still match.                                                                                                                              | Restoring a child does not restore its archived parent. It removes only that Session's archive state and preserves activity time.                                                                                            |
| Restore a Project                             | Compare `archiveRevision`, with deletion/import/export fences still respected.                                                                                                                                       | Restore the Project without clearing independently archived child Sessions. Project archive/restore advances its archive revision, not research activity time.                                                               |
| Repeat archive or use delayed Undo            | Commands still compare their captured generation/revision; timestamps are not a compare-and-set token.                                                                                                               | Repeating an already-applied archive can retry failed background cancellation. An old archive/Undo after an archive/restore round trip is rejected even when archive timestamps match.                                       |
| Ordinary save arriving after archive          | Preserve the Main-owned archive field under the normal save contract.                                                                                                                                                | Do not describe archive as a universal ban on persistence/maintenance writes. Such a save cannot restore visibility or authorize new work.                                                                                   |
| Delete a Session, including an active one     | Run the deletion preparation/quiescence and file/provenance/Compute participation protocol. Archive's “finish or stop first” predicate is not the deletion protocol.                                                 | Successful deletion fences later saves. Precommit failures can restore prepared resources; postcommit notification/cleanup errors do not recreate deleted JSON. Unreadable durable Session authority fails closed.           |
| Delete a Project                              | Persist `ProjectDeletionIntent` before destructive runtime cleanup and retain the admission fence across failed teardown.                                                                                            | Recovery retries the intent. Logical deletion and resource cleanup are separate; the existing `cleanup-pending` outcome and retry status describe unfinished cleanup. Retained provenance is not evidence of a live Session. |
| Read or recover archived/deleted data         | Archived visibility is filtered separately from deletion. Use the corresponding catalog/archived surface; never infer liveness from a retained file reference or relational origin alone.                            | Recovery reconciles existing authority and deletion evidence. It must not turn an ordinary scan into a bulk undelete.                                                                                                        |

## Persistence failures and historical data

- JSON and SQLite publication are ordered steps, not one cross-store transaction. If JSON publication
  fails on a provably new allocation with no remaining authority files or independent usage evidence,
  the repository can abort that allocation and pending intent. An existing durable fact prevents
  that compensation; sequence numbers need not be reused.
- A recognized temporary file whose live writer prevents safe recovery keeps the Session unresolved
  and the scan incomplete. Pending replay must not infer deletion from the absent primary alone.
  Revisioned saves remain blocked until authority can be recovered safely; immediate retry is not
  guaranteed. Explicit deletion with valid primary authority removes recognized temporary siblings
  before the primary, so they cannot resurrect the Session later.
- Historical files without `revision` read as zero; graph-less histories materialize on write.
  Missing Session numbers have a defined projection backfill. Missing `branchSource` stays absent;
  old Sessions do not gain one-shot details-generation eligibility. Missing `selectedComputeHosts`
  retains the legacy enabled-host selection meaning, whereas an explicit empty array means none.
- Repairing historical mistaken deletion markers is **not implemented by these fixes**. Deliberate
  deletion and abandoned allocation must be distinguished with trustworthy evidence before any
  migration or repair is proposed. The current guide adds no compatibility code or persisted state.

| Renderer local edits and incoming authority                    | [Session store tests](../src/renderer/src/stores/session-store.test.ts) cover older-timestamp archive updates, unsaved titles, runtime revisions and graph identity merges; [archive ordering tests](../src/renderer/src/stores/session-store.archive-order.test.ts) cover revision ordering.                                       |
| JSON/SQLite failure and deletion boundaries                    | [Projection tests](../src/main/session-persistence/projection.test.ts), [repository tests](../src/main/session-persistence/repository.test.ts), [Session deletion integration](../src/main/session-persistence/deletion-integration.test.ts) and [Project deletion tests](../src/main/projects/deletion-coordinator.test.ts).       |

For a new field, identify its durable owner, creation default, ordinary-save behavior, dedicated
writer, conflict handling, Renderer projection and historical missing-value meaning. Add a minimal
public-behavior regression for a demonstrated omission before fixing it. A shared shape does not
justify giving creation, normal save and privileged commands identical merge permissions.

These owner-boundary tests do not establish real multi-window Web/Electron consistency, resumability
through every supported Agent implementation, or OS power-loss durability. Those remain separate
verification tasks; the presence of a recovery flag or a passing unit test is not such a guarantee.
